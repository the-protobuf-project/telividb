Two things worth reading off this. The GPU index is 9.2× faster than CPU exhaustive and builds in 0.6 seconds against HNSW's 697 — for a corpus that fits on the device it is exact, near-instant to build, and does not degrade under deletes. And HNSW's build time is the clear weak point.

One anomaly to resolve rather than assume: exhaustive search reports 0.9994, not 1.0. Six misses per ten thousand, almost certainly f32 rounding against ground truth computed at higher precision, flipping ties at the k=10 boundary. It should be confirmed before it is quoted anywhere.

02 The gap to FAISS, honestly

FAISS is a C++ library of index structures — it has no model and no weights. What it offers that we do not is a family of index types, and the relevant question is which of those we still lack.

FAISS indexOursStatusNotes
IndexFlatIPGpuFlatIndex built One matmul over the corpus. Exact.
IndexFlatL2GpuFlatIndex built Added via the ‖a‖² − 2a·b + ‖b‖² expansion.
IndexHNSWHnswIndex built Pure Rust. Build time needs work.
Bounded top-KTopK built Not on the GPU — and §03 explains why that was the wrong idea.
IndexIVFFlatIvfFlatIndex built Coarse quantizer, inverted lists, nprobe swept at query time.

Worth knowing before planning

Product quantization is largely done. PqCodebook already implements k-means training, encode, decode and asymmetric distance computation, and PqTier exposes it through the ScanTier port. The missing pieces are the coarse quantizer and the index adapter that composes the two.

03 Finding: the bottleneck was not where this design said

Revised by measurement

This section originally argued that top-K should move to the GPU, because every query copied four megabytes of scores to the host. Profiling showed that premise is wrong, and the section is kept in corrected form rather than quietly rewritten — the mistake is the useful part.

A flat GPU query is two operations: a matmul that scores every row, and a selection that keeps the best k. Timed separately on a million-row corpus:

StageTimeWhat it is
matmul, device-resident2.17 msScoring every row.
+ 4 MB copy to host0.13 msNearly free — unified memory.
host Vec build + select2.13 msThe actual cost.
streaming top-k0.27 msSame result, bounded state.

The copy costs a tenth of a millisecond. On Apple silicon the GPU and CPU share memory, so there is no transfer to eliminate — the design was reasoning about a discrete card's cost model on hardware that does not have one. What actually cost 2.13 ms was building a one-million-element Vec<Candidate> in order to discard all but ten of them.

That is a CPU problem. Moving top-K to the GPU would have fixed nothing and added a device-side masking path to keep invariant 15's filter-before-select guarantee.

It would not have worked anyway

candle's arg_sort_last_dim dispatches a single threadgroup whose width is the padded column count, with that many floats of threadgroup memory. At a million columns that asks Metal for a 1,048,576-wide threadgroup — against a limit of 1024 — and four megabytes of threadgroup memory against roughly thirty-two kilobytes. There is no branch to the multi-block path. The proposal was doubly wrong.

What was actually done

A bounded selector already existed in domain/top_k.rs — same heap, same reasoning — but only the two-tier scan used it, while both exhaustive indexes collected every row. Wiring it into flat.rs and gpu/search.rs was the whole fix, plus an early-out so a losing row costs one comparison rather than a push and a pop.

A side effect worth having: the CPU and GPU indexes now rank identically by construction, because they run the same selector with the same deterministic tie-break, rather than two sorts that happen to agree.

Where the remaining time goes

The matmul reads 512 MB of f32 corpus in 2.17 ms — about 227 GB/s, close to this machine's ceiling. It is memory-bandwidth-bound, so the only lever left is fewer bytes: f16 halves it, and product quantization cuts it far further. That reframes §05 as the main performance work rather than merely a capacity feature.

04 IVF: partitioning the corpus

Exhaustive search costs O(N) per query. An inverted file trades a little recall for a large constant factor: cluster the corpus once, then search only the few clusters nearest the query.

nprobe is the accuracy dial, exactly as ef_search is for HNSW — a query-time value that needs no rebuild, so the benchmark can sweep it into a recall-versus-throughput curve.

Read honestly: HNSW wins the search curve at this scale — it reaches full recall at 19,007 queries per second where IVF needs to probe every list to match, at 7,158. What IVF wins is build time, by 5.3×, and that is the trade it exists to make. Its real advantage arrives with quantization, where the corpus stops having to fit in memory uncompressed.

Constraint that shapes the design

Centroids must be per-segment. The project's own gotcha list is explicit: a shared centroid table is cross-segment state, and it silently breaks scatter-gather and forecloses clustering. Each sealed segment therefore trains and stores its own centroids, and a query probes every segment independently — which is what the existing merge step already expects.

k-means already exists in format/quantize/pq/kmeans.rs, written for PQ subspace training. The coarse quantizer is the same algorithm over full vectors, so the reusable part is real and the new code is the inverted lists and the probe path.

05 IVF-PQ: 64× smaller rows

IVF cuts how many rows are scored; PQ cuts what each row costs to store and to score. Each row is encoded relative to its own list's centroid, because residuals are small and centred where absolute vectors are spread across the whole space — that is most of why IVF-PQ beats PQ alone at equal code size.

ConfigurationRecall@10Queries/sBytes/row
ivf-pq nprobe=40.849023,2388
ivf-pq nprobe=160.93908,5918
ivf-pq nprobe=640.93902,3688
flat (f32)1.00001,403512

Recall plateaus at 0.939, and that plateau is the point worth understanding: it is the quantization ceiling, not a probing limit. Probing more lists cannot recover what the codes discarded — only a wider exact rescore can, which is why the two dials are separate and why a test now pins that they do different jobs.

Reaching this required moving PqCodebook into telividb-distance, since the index crate may not depend on storage. Its serialization stayed behind, because magic bytes and a format version are rule 4's concern while the arithmetic is not.

06 GPU IVF-PQ: measured, and abandoned

Not built, deliberately

This step proposed moving ADC scoring to the device as a gather and a segmented sum. Measurement says it would be slower at every scale, so it was not written. This is the second premise in this document that profiling refuted — see §03 for the first.

Rows scoredCPUGPUWinner
1,0000.004 ms0.474 msCPU
10,0000.017 ms0.434 msCPU
100,0000.160 ms0.991 msCPU
1,000,0001.612 ms3.231 msCPU

The reason is structural rather than incidental. ADC is a memory-bound gather with almost no arithmetic — eight lookups and seven adds per row — against roughly 0.43 ms of fixed dispatch overhead. And IVF exists precisely to make the work small: at a million rows with a thousand lists and nprobe of sixteen, a query touches about sixteen thousand rows, where the CPU takes 0.017 ms and the device takes 0.43 ms. Twenty-five times slower, at exactly the size that matters.

GPU and IVF-PQ want opposite things. One wants a single large contiguous operation; the other deliberately produces small scattered ones.

What does pay off: batching queries

One query against an exhaustive corpus is a mat-vec, which cannot fill the device. Many queries at once is a matmul, which can — and a server answering concurrent requests has many.

5.5× per query at a batch of 32, on the exhaustive path that already exists. The regression at 128 is its own lesson: the score matrix becomes 512 MB to return, so the copy that was free at one query stops being free.

This is a change to the VectorIndex port, which takes a single query — so it belongs in a proposal rather than in a commit.

07 Where each operation actually belongs

The question "should every index run on the GPU" has a measured answer, and it is not the one the phrasing suggests. Each operation was timed where it could run, and the split below is the result rather than a compromise.

OperationRuns onWhy
Exhaustive scoringGPU 512 MB read as one contiguous matmul — 2.17 ms against 47 ms on CPU.
Top-k selectionCPU Bounded heap at 0.27 ms; a device sort cannot address a million columns at all.
ADC code scoringCPU Memory-bound gather, almost no arithmetic. 25× faster than the device.
Graph traversalCPU Each hop depends on the last — the access pattern a GPU is worst at.

Why IVF on the GPU is not worth building

IVF-Flat scores full vectors, which is matmul-shaped — so unlike ADC it looked like a real candidate. Measured against a device-resident corpus of a million rows:

Rows probedCPUGPU, partitionedGPU, exhaustive
1,000 (0.1%)0.146 ms11.935 ms2.17 ms
16,000 (1.6%)2.661 ms2.271 ms2.17 ms
100,000 (10%)15.142 ms8.482 ms2.17 ms

The last column is the one that settles it. Partitioning on the GPU is slower than not partitioning — gathering a subset costs more than scoring the entire corpus, at every probe size. IVF exists to avoid work that the GPU does not find expensive in the first place.

So the families divide by where, not by preference: the GPU's index is flat and batched; partitioned and graph indexes are the CPU's, and they are what a corpus too large for device memory needs regardless.

Batched exhaustive search

Built. VectorIndex gained a search_batch whose default answers queries one at a time — correct for every index, and what a graph index wants anyway — with the GPU index overriding it to read the corpus once for the whole batch. 5.5× per query at a batch of 32, with results identical to answering them singly, which eight tests pin across all three metrics.

08 What this does not address

Stated plainly, because a design that only lists its strengths is not a design.

  • Filtered search. The place vector databases differ most in production, and none of the above improves it. A GPU fast path that falls back whenever a predicate is present arguably makes the gap wider.
  • Concurrency. Every figure here is single-threaded. A serving system is not.
  • Recall under deletes. HNSW degrades as tombstones accumulate; IVF lists become unbalanced. Neither is measured.
  • Comparison against FAISS itself. Cross-machine benchmark numbers are not comparable. The only honest comparison is running it on this hardware, on this dataset.

Measured with examples/rust/src/bin/ann on SIFT-1M (128-dim, 1,000 queries, exhaustive ground truth), Apple M3 Max, 30-core GPU, 36 GB, macOS 26.6.2. Reproduce with examples/datasets/download.sh sift.
